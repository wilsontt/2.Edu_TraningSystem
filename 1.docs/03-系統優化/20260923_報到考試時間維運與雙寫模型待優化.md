## 4. 名詞解釋

| 名詞 | 說明 |
|------|------|
| **現況表** | 每人×每計畫一列、可覆寫的當下狀態（如 `attendance_records`、`exam_records`） |
| **歷程表** | append-only 事件／每次交卷快照（如 `attendance_checkin_events`、`exam_history`） |
| **naive UTC** | DB 存 UTC 牆鐘時間但**無**時區標記（例：`2026-09-23 03:08:05`）；畫面台北為同瞬間 +8（`11:08:05`） |
| **計畫日** | `training_date`／`end_date`：純 `Date`，**不做** UTC±8 換算 |

## 5. 作業內容

### 5.1 今日發現的問題（現象）

1. **計畫開始日**：`PUT /plans/{id}` 若變更 `training_date` 且已有 `exam_records` → HTTP 400「已有學員開始考試，無法變更開始日期」（`backend/app/routers/training.py`）。結束日 `end_date` 無此鎖。
2. **報到統計畫面**：只改 `attendance_records.checkin_time` **不夠**。報到總覽列表優先顯示 `latest_event_time`（來自 `attendance_checkin_events.event_time`），故畫面仍顯示舊日。
3. **成績中心「提交時間」**：來自 `exam_records.submit_time`（同 UTC 慣例）；有重考則另有 `exam_history`。
4. **時區**：DB 比台北畫面早 8 小時屬**預期行為**，非存錯。維運改時間時須寫 **UTC（台北 − 8）**，不可把台北鐘點直接寫入。

### 5.2 現況維運路徑（無 UI 時）

> 正式環境操作前：完整備份 `data/education_training.db`（或容器掛載之正式 DB）。

**A. 查 `plan_id`**

```sql
SELECT id AS plan_id, title, training_date, end_date, year
FROM training_plans
WHERE title = '2026安全程式開發訓練計畫';
-- 實例：id = 3
```

**B. 報到日期改對齊計畫日（僅改日期、保留既有 UTC 時分秒）**

```sql
UPDATE attendance_records
SET checkin_time = '2026-07-27 ' || substr(checkin_time, 12)
WHERE plan_id = 3;

UPDATE attendance_checkin_events
SET event_time = '2026-07-27 ' || substr(event_time, 12)
WHERE plan_id = 3;
```

**C. 成績中心提交／開始時間**

```sql
UPDATE exam_records
SET submit_time = '2026-07-27 ' || substr(submit_time, 12),
    start_time  = CASE
      WHEN start_time IS NOT NULL
      THEN '2026-07-27 ' || substr(start_time, 12)
      ELSE start_time
    END
WHERE plan_id = 3;

UPDATE exam_history
SET submit_time = '2026-07-27 ' || substr(submit_time, 12)
WHERE record_id IN (SELECT id FROM exam_records WHERE plan_id = 3);
```

**D. 畫面與資料對照**

| 畫面 | 主要讀取 |
|------|----------|
| 報到統計「報到時間」（報到總覽） | `latest_event_time` ← `attendance_checkin_events`；否則 `checkin_time` |
| 訓練計畫管理內報到統計 | 多以 `attendance_records.checkin_time` |
| 成績中心「提交時間」 | `exam_records.submit_time` |
| 考試歷程 Modal | `exam_history`（舊資料可能回退顯示 record） |

### 5.3 延伸架構問題（待優化）

#### 問題 A：現況＋歷程雙寫 → 維運易漏改

| 領域 | 現況表 | 歷程表 | 痛點 |
|------|--------|--------|------|
| 報到 | `attendance_records` | `attendance_checkin_events` | 改現況畫面不變；註解亦寫明不覆蓋 `checkin_time` |
| 考試 | `exam_records` | `exam_history` | 交卷覆寫 record + 另插 history；改時間須雙邊；舊資料可能無 history |

設計演進：先有現況表滿足「一人一計畫一狀態」與統計；後加歷程／重考，採旁掛而非重做讀路徑 → **短期改動小、長期同步成本高**。

#### 問題 B：考試「只要歷程一張表」是否更乾淨？

**概念上較乾淨**（建議日後評估）：

```text
exam_attempts（每次考試一列）
  emp_id, plan_id, attempt_no, start_time, submit_time, score, is_passed, …
「最新成績」= 同 emp+plan 聚合（最新 submit 或 is_current）
「可否重考」= 掛在 plan+emp 維度或授權表
```

**現況不能直接刪 `exam_records` 的原因**：

- 進行中考試（已 `start_exam`、尚無 `submit_time`）
- `exam_details` 掛在 record（最新題目明細）
- `retake_authorized`、`exam_retake_authorizations` 掛 record／history id
- 成績中心／考試中心／統計大量讀 record

#### 問題 C：缺少管理端「時間校正」能力

業務合理需求：計畫日誤開、報到／交卷日需對齊訓練日。目前僅能 SQL；風險含漏改歷程、寫錯時區、無稽核。
